Notes présentateur

git → Linear, avec n8n en local — à usage personnel, ouvrir sur ton téléphone ou un second écran pendant la présentation.

Checklist avant de commencer

Le process complet, du terminal à Linear

Tout commence quand je tape git-sync dans mon terminal, à la racine du projet. Le script lit d'abord l'état de mon dépôt git en local : la branche sur laquelle je suis, les commits pas encore envoyés (grâce à un petit fichier marqueur caché dans .git/), les fichiers modifiés, et la clé d'équipe Linear à utiliser (lue dans le fichier .n8nsync à la racine). Si un de mes commits contient le mot-clé closes-all, le script fait une étape de plus avant même de contacter n8n : il exécute en local, sur ma propre machine, la commande de test définie dans .n8ntest (par exemple npm test dans demo-book-crud), et récupère le résultat réel, réussite ou échec, de chaque vérification. Tout ce travail, jusqu'ici, se passe entièrement sur mon ordinateur, sans aucun appel réseau.

Le script assemble ensuite toutes ces informations (dépôt, branche, commits, fichiers, et éventuellement le résultat des tests) dans un unique message au format JSON, et l'envoie par une requête HTTP POST vers l'adresse http://localhost:5678/webhook/git-sync. Cette adresse pointe vers le conteneur Docker n8n qui tourne en permanence sur ma machine. Le serveur HTTP intégré à n8n reçoit cette requête, reconnaît le chemin /webhook/git-sync grâce au nœud "Webhook" du workflow, et déclenche une nouvelle exécution de ce workflow avec les données reçues.

Le moteur de n8n parcourt alors le workflow nœud par nœud, en suivant les flèches (les "connections"). Un premier nœud de code analyse le nom de la branche et les messages de commit à la recherche d'un identifiant de ticket du type PAR-5. Si cet identifiant est trouvé, le workflow part directement interroger l'API de Linear pour récupérer ce ticket précis. S'il n'est pas trouvé, le workflow part sur un autre chemin qui ferait appel à Claude pour deviner le bon ticket parmi ceux ouverts, un chemin qu'on laisse de côté aujourd'hui puisque Claude n'est pas connecté.

Une fois le ticket identifié, le workflow appelle l'API GraphQL de Linear à plusieurs reprises : d'abord pour faire passer le ticket à l'état "In Progress", puis pour y ajouter un commentaire qui liste les commits envoyés. Si le mot-clé closes-all était présent et que le résultat des tests reçu plus tôt indique que tout est passé, une branche supplémentaire du workflow se déclenche en parallèle pour faire passer le ticket à l'état "Done", avec un commentaire récapitulatif des vérifications. Pendant ce temps, n8n a déjà renvoyé une réponse HTTP à mon terminal, ce qui explique pourquoi le message affiché dit toujours "In Progress" même quand le ticket finit, l'instant d'après, en Done.

Enfin, si tout s'est bien passé (réponse HTTP 200), le script git-sync met à jour son marqueur local avec le dernier commit envoyé, pour ne jamais renvoyer deux fois le même travail au prochain lancement.

  • Aller vite, 1 minute max
  • Un workflow = une suite de nœuds reliés par des flèches, qui s'exécute automatiquement
  • 4 types de nœuds suffisent : Déclencheur, Logique (IF), Code, Action (appel API)

Questions probables et réponses

« Et si l'IA se trompe de ticket ? »
Sous 0,7 de confiance, rien n'est modifié. Et tout est réversible : un changement de statut et un commentaire, rien de destructif.
« Ça coûte combien en API ? »
De l'ordre du centime par appel, et seulement quand la branche ne nomme pas déjà le ticket (sinon zéro appel IA).
« Pourquoi pas l'intégration GitHub native de Linear ? »
Elle est très bien quand l'identifiant du ticket est déjà dans la branche. Elle ne fait rien quand il n'y est pas, et c'est précisément le cas fréquent.
« Qui maintient ça ? »
Vraie question. Un workflow non maintenu est une dette. C'est l'argument pour le mettre sur un serveur partagé et versionner son export plutôt que de le laisser sur un portable.
« Vos données partent chez Anthropic ? »
Les messages de commit et les noms de fichiers, oui. Jamais le code. Si c'est bloquant, le rapprochement par référence directe fonctionne seul, sans aucun appel IA.
« Le passage en Done, c'est fiable ? »
Ce n'est pas une estimation : de vrais tests tournent en local, sur la machine du développeur, avant même que quoi que ce soit parte vers n8n. n8n lit un résultat réel (pass/fail), jamais une supposition.
« N'importe qui peut écrire closes-all et forcer un Done ? »
Le mot-clé seul ne suffit pas : il faut en plus que les tests réels passent à 100%. Double verrou : un geste volontaire du développeur, plus une vérification réelle.
« On peut l'utiliser sur un autre projet ? »
Oui. git-sync est installé globalement sur la machine. Il suffit d'un fichier .n8nsync différent à la racine de l'autre dépôt pour cibler une autre équipe Linear. Le même workflow n8n peut servir plusieurs projets.
« Et sans clé Anthropic connectée (comme aujourd'hui) ? »
Ça fonctionne quand même pour le cas courant : tant que l'identifiant du ticket est dans le nom de la branche, aucun appel IA n'est nécessaire. Claude ne sert que si on oublie de le faire.

Pense-bête — commandes de démo

Démo 1 — PAR-8 (health-check)

git checkout main
git checkout -b feat/par-8-health
git add demo-book-crud/src/health demo-book-crud/src/app.ts
git commit -m "feat(health): add health-check endpoint (PAR-8)"
git-sync

Démo 2 — PAR-9, premier commit (suivi continu, partie 1)

git checkout main
git checkout -b feat/par-9-loans
git add demo-book-crud/src/loans/store.ts
git commit -m "feat(loans): add in-memory store (PAR-9)"
git-sync
Vrai commit (juste le fichier de stockage). Attendu : PAR-9 passe en In Progress, 1er commentaire ajouté.

Démo 2 — PAR-9, deuxième commit (suivi continu, partie 2)

git add demo-book-crud/src/loans/routes.ts
git commit -m "feat(loans): add CRUD routes (PAR-9)"
git-sync
Deuxième vrai commit (les routes, un fichier différent). Attendu : toujours In Progress, un 2e commentaire s'ajoute au premier.

Démo 3 — PAR-9, commit final (passage en Done)

git add demo-book-crud/src/app.ts demo-book-crud/src/health demo-book-crud/src/reviews demo-book-crud/test.mjs demo-book-crud/package.json demo-book-crud/src/books/store.ts demo-book-crud/README.md
git commit -m "feat(loans): wire routes and acceptance tests (closes-all) (PAR-9)"
git-sync --all
Troisième vrai commit (le branchement + les tests). Attendu : les tests réels tournent en local, puis PAR-9 passe en Done dans Linear (le terminal affichera quand même "In Progress", voir démo 3 plus haut).
Pour rejouer plusieurs fois : remets PAR-8/PAR-9 en Backlog dans Linear, puis git checkout main && git branch -D feat/par-8-health feat/par-9-loans avant de recommencer.
