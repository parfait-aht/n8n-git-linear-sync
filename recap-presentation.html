Le board Linear se met à jour quand tu commites.

Un workflow n8n lit tes commits, retrouve le ticket correspondant et le met à jour. Ce récap reprend les notions de la présentation, l'installation complète et la démo. Il accompagne les slides.

$ git-sync -> 2 commit(s) sur feat/PAR-5-books-crud (commits non pousses) Ticket PAR-5 -> In Progress (2 commit(s)) https://linear.app/equipe/issue/PAR-5
Backlog→ In Progress→ Done

Le ticket avance de lui-même : un commit le passe en In Progress, un commit (closes-all) avec des tests réussis le passe en Done.

Le problème et l'idée

Le board Linear ne reflète presque jamais la réalité. Un dev commence une tâche, le ticket ne bouge pas (ou n'existe pas encore), et le chef de projet n'a aucune visibilité sur ce qui avance.

Ce n'est pas un problème de discipline, c'est un problème d'incitation : celui qui déplace la carte n'en tire aucun bénéfice.

Le seul geste demandé au dev est celui qu'il fait déjà : commiter. Le reste est automatique.

Ce que fait le système

Action du devEffet dans Linear
git-sync sur une branche qui contient l'identifiant (feat/PAR-5-...)Le ticket PAR-5 passe en In Progress et reçoit un commentaire listant les commits. Aucune IA n'intervient.
Plusieurs git-sync sur le même ticketUn commentaire s'ajoute à chaque fois. Le statut ne bouge pas : il ne change que si le dev le décide.
Un commit contenant (closes-all)Les tests tournent en local. S'ils passent tous, le ticket passe en Done avec un récap des vérifications. Sinon il reste en In Progress.
Aucun identifiant dans la branche (chemin optionnel)Claude lit les tickets ouverts et propose le plus proche. Au-dessus de 0,7 de confiance, le ticket est utilisé. Sinon un nouveau ticket est créé.

Tout est réversible : le workflow ne fait que changer un statut et ajouter un commentaire, rien de destructif.

Les notions à connaître

n8n et workflow

n8n est un outil d'automatisation. Un workflow est une suite de nœuds reliés par des flèches, qui s'exécute quand un événement le déclenche. Quatre types de nœuds suffisent ici :

  • Déclencheur : démarre le workflow (le webhook).
  • Logique (IF) : choisit un chemin (« référence trouvée ? »).
  • Code : calcule ou analyse (« analyser le contexte »).
  • Action : appelle une API (Linear, Anthropic).
Webhook
Une adresse HTTP qui attend des données. git-sync envoie un POST à http://localhost:5678/webhook/git-sync ; n8n reconnaît ce chemin et lance une exécution du workflow.
Architecture de n8n
Trois briques : le moteur qui exécute le workflow nœud par nœud, les nœuds qui font le travail, et le serveur HTTP qui reçoit les appels. Le workflow est un fichier JSON (un tableau nodes, un objet connections), exactement ce que le moteur exécute. On peut donc le versionner dans git.
Postgres
n8n y stocke ses workflows, ses identifiants chiffrés et l'historique des exécutions. Le nom postgres est du DNS interne Docker standard. La démo demo-book-crud n'utilise pas ce Postgres, ses données sont en mémoire.
États d'un nœud
Actif ou désactivé est un choix de configuration. Succès, erreur ou non atteint est le résultat d'une exécution. L'onglet Executions sert de diagnostic : on y voit les données qui ont traversé chaque nœud.
Seuil de confiance
Quand Claude rapproche un commit d'un ticket, il renvoie un score entre 0 et 1. En dessous de 0,7, rien n'est modifié sur un ticket existant.
Double verrou du Done

Un ticket ne passe en Done que si les deux conditions sont réunies :

  1. le dev a écrit volontairement closes-all dans un commit ;
  2. une vraie commande de test, exécutée en local, renvoie des vérifications toutes réussies.

n8n lit un résultat pass/fail réel. Il ne devine jamais.

Le parcours complet, du terminal à Linear

Les cercles pleins se passent sur ta machine, avant tout appel réseau. Les cercles vides se passent dans n8n ou chez Linear.

  1. 1Le dev tape git-synclocal

    À la racine du projet.

  2. 2Le script lit l'état du dépôtlocal

    Branche, commits pas encore envoyés (marqueur dans .git/n8n-last-sync), fichiers modifiés, clé d'équipe (fichier .n8nsync).

  3. 3Si un commit contient closes-all, les tests tournentlocal

    La commande de .n8ntest s'exécute sur la machine et le résultat réel de chaque vérification est récupéré.

  4. 4Le script envoie un JSON à n8nlocal

    POST vers localhost:5678/webhook/git-sync, le conteneur Docker qui tourne sur la machine.

  5. 5n8n déclenche le workflown8n

    Un nœud Code cherche un identifiant du type PAR-5 dans la branche et les messages de commit.

  6. 6Le ticket est identifién8n

    Trouvé : n8n interroge l'API GraphQL de Linear. Non trouvé : le chemin optionnel passe par Claude (rapprochement ou création).

  7. 7Linear est mis à jourLinear

    Passage en In Progress, puis commentaire listant les commits.

  8. 8Passage en Done si les deux verrous sont réunisLinear

    Une branche parallèle passe le ticket en Done avec un commentaire récapitulatif des vérifications.

  9. 9Le marqueur local est mis à jourlocal

    Seulement si n8n a répondu 200. Un échec ne perd aucun commit, et relancer git-sync ne crée pas de commentaire en double.

Le terminal affiche toujours « -> In Progress », même quand le ticket finit en Done juste après : la réponse HTTP part avant la fin de l'évaluation. Le vrai résultat est dans Linear.

Architecture

git-sync (script bash, sur ta machine)
   │  branche, commits, fichiers modifiés (+ résultat des tests si closes-all)
   ▼
POST localhost:5678/webhook/git-sync   →   n8n (Docker + Postgres)
   │
   ├─ identifiant de ticket dans la branche ? ── oui ──► Linear (API GraphQL)
   └─ non ─► Claude (optionnel) ─────────────────────────► Linear
                                                           │
                          In Progress + commentaire  →  Done si closes-all + tests OK
  • Tout est local. n8n tourne en Docker sur la machine, aucun port exposé sur Internet, aucun tunnel.
  • Les tests tournent avant l'envoi. n8n ne lit jamais le code, seulement un résultat pass/fail.
  • Deux appels sortent de la machine : Linear et, en option, Anthropic. Claude ne voit que des noms de fichiers et des messages de commit.

Installation

Prérequis : Docker, jq, un compte Linear. La clé API Anthropic est optionnelle, elle ne sert qu'au rapprochement par IA. Le reste (In Progress, commentaires, Done via tests réels) fonctionne sans.

  1. Installer n8n en local

    10 minutes · docs/01-installation.md

    cd docker
cp .env.example .env

# génère les deux secrets, puis remplace les REMPLACE_MOI dans .env
echo "POSTGRES_PASSWORD=$(openssl rand -hex 16)"
echo "N8N_ENCRYPTION_KEY=$(openssl rand -hex 32)"

docker compose up -d
docker compose ps    # n8n et postgres : running, postgres (healthy)

    Ouvre http://localhost:5678 et crée le compte propriétaire. Il est local à ta machine, sans lien avec n8n Cloud.

    La clé N8N_ENCRYPTION_KEY est le point critique. n8n s'en sert pour chiffrer tes identifiants. Perdue ou modifiée après le premier démarrage, elle les rend illisibles, même dans une sauvegarde. Garde-la dans un gestionnaire de mots de passe. Le fichier .env n'est jamais versionné.

  2. Créer les identifiants

    10 minutes · docs/02-credentials.md

    • Linear : Settings → Security & access → Personal API keys. Dans n8n : Credentials → type Linear API, nom Linear, authentification API Token, puis Test.
    • Anthropic (optionnel) : crée une clé sur la console Anthropic. Dans n8n : Credentials → Header Auth, nom Anthropic, Name x-api-key, Value = la clé sk-ant-....
    • Note la clé d'équipe Linear : le préfixe de tes tickets (PAR dans PAR-5).

  3. Mettre en place le workflow

    5 minutes en important, 1 h 30 en le construisant · docs/03-workflow.md

    Le plus rapide : importer workflows/git-linear-sync.json (menu ⋯ en haut à droite → Import from File), puis rattacher le credential Linear à chaque nœud Linear (plus aucun triangle rouge). Active ensuite le workflow avec l'interrupteur Active.

  4. Installer le script git-sync

    10 minutes · docs/04-script-git-sync.md

    ln -sf <chemin-du-depot>/bin/git-sync /usr/local/bin/git-sync
# Apple Silicon, si /usr/local/bin n'est pas dans le PATH :
# ln -sf <chemin-du-depot>/bin/git-sync /opt/homebrew/bin/git-sync

which git-sync && git-sync --help

# dans le dépôt du projet
echo "PAR" > .n8nsync
    CommandeEffet
    git-syncUsage normal
    git-sync --dry-runAffiche ce qui serait envoyé, sans appeler n8n
    git-sync --allIgnore le marqueur et renvoie toute la branche
    git-sync --team WEBForce la clé d'équipe

  5. Activer le passage en Done (optionnel)

    Crée un fichier .n8ntest à la racine du projet, avec une seule ligne : la commande de test.

    echo "cd demo-book-crud && npm test" > .n8ntest

    Cette commande doit afficher, sur la dernière ligne de sa sortie, un JSON de cette forme :

    {"allPassed": true, "results": [{"name": "...", "passed": true}]}

  6. Valider avant de présenter

    30 minutes · docs/05-tests.md

    Cinq scénarios : ticket nommé dans la branche, rapprochement par IA, création de ticket, idempotence (relancer git-sync ne renvoie rien), passage en Done. Le document contient aussi un tableau de diagnostic des erreurs fréquentes.

La démo

Le projet demo-book-crud

Une petite API REST en TypeScript avec Hono, au stockage en mémoire. Son but est de produire de vrais commits à synchroniser, pas de livrer un service de production. Chaque ressource correspond à un ticket Linear :

TicketRessource
PAR-5Livres (/books)
PAR-6Auteurs (/authors)
PAR-7Avis sur les livres (/reviews)
PAR-8Health-check (/health)
PAR-9Emprunts (/loans)
 
cd demo-book-crud
npm install
npm start            # lance l'API
npm test             # toutes les vérifications
npm run test:books   # une ressource à la fois

Chaque test correspond à un critère d'acceptation d'un ticket. Son résultat réel (pass/fail, jamais une estimation) est lu par git-sync via .n8ntest pour décider du passage en Done.

Préparation avant de démarrer

  • docker compose ps : n8n et postgres tournent.
  • Le workflow est Published, tous les nœuds Linear ont leur credential.
  • Les tickets de démo (par exemple PAR-8 et PAR-9) sont en Backlog dans Linear.
  • Trois onglets ouverts : n8n, Linear (vue board), terminal.
  • unset N8N_WEBHOOK_URL pour repasser sur l'URL de production.
  • ./setup-demo-book-crud.sh lancé une fois à la racine du dépôt, juste avant de commencer : il recrée les fichiers de démo non committés.
  • Branches et commits préparés à l'avance, rien n'est tapé en direct.

Déroulé

  1. 1La douleur

    On ouvre le board Linear et on demande s'il reflète ce sur quoi l'équipe travaille. On laisse le silence répondre.

  2. 2La promesse

    Le board se met à jour tout seul à partir de la seule chose qu'un dev fait toujours : commiter.

  3. 3Démo 1 : le cas simple

    Branche qui nomme le ticket. git log --oneline -3 puis git-sync. On rafraîchit Linear : le ticket est en In Progress, avec le commentaire des commits. Aucune IA, n8n a lu le nom de la branche.

  4. 4Démo 2 : le suivi continu

    Deux ou trois commits sur le même ticket, chacun suivi d'un git-sync. Les commentaires s'accumulent, le statut reste en In Progress.

  5. 5Démo 3 : le passage en Done

    On montre le commit (closes-all), puis git-sync. Les tests tournent en local avant l'envoi. On rafraîchit Linear : le ticket est en Done, avec le récap des vérifications.

  6. 6n8n en deux mots

    Le workflow dézoomé (21 nœuds, aucune ligne de code déployée) et l'onglet Executions.

  7. 7Ce que ça coûte, puis clôture

    Voir la section suivante.

Le déroulé exact et le pense-bête de commandes sont dans presentation/notes-presentateur.html.

Aller plus loin

  • Serveur partagé. Pour que toute l'équipe en profite, n8n peut passer sur un VPS. La procédure et la configuration de sécurité sont dans docs/07-vps.md.
  • Hook pre-push. Il déclenche git-sync à chaque push. Le || true est volontaire : une panne de n8n ne doit jamais bloquer un push.
  • Maintenance. Un workflow non maintenu devient une dette. Versionner son export (workflows/git-linear-sync.json) évite qu'il ne vive que sur un portable.
